# 编排中心开发指南

## 1. 特性介绍

编排中心是一个面向多智能体（Agent）协作的可视化编排平台，支持通过图形化工作流设计器定义 Agent 之间的调用关系与执行流程。后端基于 Python 框架解析流程并驱动 Agent 协同工作。

本特性允许用户为不同操作定义自定义实现，同时为常见操作提供默认实现。通过统一的抽象基类和处理器注册机制，开发者可以扩展系统功能，无需修改核心代码。
除上述自定义实现以外，本特性提供可扩展的大模型（LLM）接入框架，通过进程环境变量或仓库根目录 `.env` 配置。

## 2. 约束与限制

- **操作限制**：
  - 自定义处理器注册时应在应用启动时完成，避免在业务处理过程中注册
  - LLM 参数从环境变量读取；新接口协议通过注册 provider profile 扩展。

## 3. 环境要求

- Python 3.12+

### 3.1 搭建环境

该模块设计为Python项目的组成部分。确保以下文件在项目目录中：

**自定义处理器模块：**
- `default_handle.py` - 包含基类、注册表和默认处理器
- `custom_handle.py` - 自定义处理器扩展模块（如需要）

**LLM 模块：**

- `common/llm/llm.py` - 统一工厂函数
- `common/llm/config/model_sources.py` - 环境配置来源与 provider profiles
- `common/llm/config/llm_config.py` - ModelConfig dataclass
- `common/llm/provider/auth_strategies.py` - Header 签名策略
- `common/llm/provider/generic_llm.py` - 通用 LLM Provider
- `.env` - 本地 LLM 配置（不提交）

## 4. 使用场景

### 4.1 自定义处理器使用说明

#### 4.1.1 功能介绍

**核心能力：**
- **抽象基类**：为所有处理器定义统一接口
- **默认实现**：为常见操作提供内置处理器
- **自定义扩展**：支持用户注册自定义处理器

**系统架构：**
系统采用注册表模式，核心组件包括：

| 组件 | 职责 |
|------|------|
| BaseHandler | 定义所有处理器的统一抽象接口 |
| HandlerRegistry | 管理处理器注册和获取，提供默认实现兜底 |
| InterfaceType | 定义支持的接口类型枚举 |
| 默认处理器 | 为常见操作提供内置实现 |
| 自定义处理器 | 用户扩展实现，覆盖默认行为 |

```text
┌─────────────────┐
│   业务调用方     │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ HandlerRegistry │◄──── 注册自定义处理器
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   BaseHandler    │
│   (抽象基类)     │
└────────┬────────┘
     ┌───┴───┬───────────────┐
     ▼       ▼               ▼
┌───────┐ ┌───────┐  ┌───────────┐
│ 默认  │  │ 默认 │   │  自定义   │
│处理器1│  │处理器2│  │  处理器3  │
└───────┘ └───────┘  └───────────┘
```

#### 4.1.2 何时需要自定义处理器

以下场景需要用户自行实现自定义处理器：

| 场景 | 说明 | 示例 |
|------|------|------|
| 数据库持久化 | `persistence_mode=postgresql` 或 `mysql` 选择内置 SQL 处理器 | PostgreSQL/MySQL 存储 PSOP 和执行记录 |
| 自定义存储介质 | 使用本服务未内置的后端时，需要实现相应存储处理器 | MongoDB 或 Redis 存储集成 |
| 存储逻辑定制 | 当需要在保存/查询/删除操作中添加额外业务逻辑时，需自定义处理器扩展默认行为 | 在保存 PSOP 时添加审计日志记录 |

**配置说明：**

在 `etc/conf/server.conf` 中配置 `persistence_mode` 参数：

```properties
persistence_mode=file  # 使用默认文件存储，无需自定义处理器
persistence_mode=postgresql  # 使用内置 PostgreSQL 处理器
persistence_mode=mysql       # 使用内置 MySQL 处理器（8.0.19+）
```

数据库模式选择已注册的 SQL 处理器；未知模式会在启动时被拒绝。MySQL 的配置与存储边界见 [MySQL 持久化配置](MySQL持久化配置.md)。

#### 4.1.3 开发步骤
步骤1：引入所需模块
```python
from common.custom.default_handle import BaseHandler, HandlerRegistry, InterfaceType
```

步骤2：创建自定义处理器

创建继承自BaseHandler的自定义类，并实现handle方法：
```python
class MyCustomHandle(BaseHandler):
    """自定义处理器示例"""
    
    def handle(self, *args, **kwargs):
        """
        自定义处理逻辑
        
        Args:
            *args: 位置参数
            **kwargs: 关键字参数
            
        Returns:
            处理结果
        """
        # 自定义实现
        # 建议：在这里添加具体的业务逻辑
        # 注意：确保方法是异步的
        result = "自定义结果"
        return result
```
步骤3：注册自定义处理器

在应用启动时注册自定义处理器：
```python
# 注册自定义处理器
# 注意：注册操作应在业务处理开始前完成
HandlerRegistry.register(InterfaceType.GET_PSOP_BY_ID, MyCustomHandle)
```
警告：后注册的处理器会覆盖同类型的先前处理器。请确保注册顺序符合预期。

步骤4：使用处理器

在业务代码中获取并使用处理器：
```python
# 获取处理器实例
# HandlerRegistry会自动返回已注册的自定义处理器或默认实现
handle = HandlerRegistry.get_handler(InterfaceType.GET_PSOP_BY_ID)

# 使用处理器执行业务
result = handle.handle(...)
```
步骤5：完整示例

以下是一个完整的自定义处理器实现示例：
```python
from common.custom.default_handle import BaseHandler, HandlerRegistry, InterfaceType

class SaveCustomHandle(BaseHandler):
    """自定义查询处理器"""
    
    def handle(self, query_params=None):
        """
        自定义查询逻辑
        
        Args:
            query_params: 查询参数字典
            
        Returns:
            查询结果列表
        """
        # 示例：实现自定义查询逻辑
        if not query_params:
            return []
        
        # 自定义查询实现
        results = []
        # ... 业务逻辑
        return results

# 注册
HandlerRegistry.register(InterfaceType.SAVE_PSOP, SaveCustomHandle)

# 使用
handler = HandlerRegistry.get_handler(InterfaceType.SAVE_PSOP)
data = handler.handle({"id": 1})
print(data)
```

### 4.2 LLM 模块配置说明

Chat、Embedding、Reranker 的模型定义从 `etc/config/models.yaml` 读取，密钥从进程环境变量或仓库根目录的 `.env` 读取；环境变量优先，空值不会覆盖 `.env`。完整配置见 [LLM 配置说明](../../etc/config/README_zh.md) 和 [`.env.example`](../../.env.example)。

`models:` 下的每个键是一种能力（`chat`、`embed`、`rerank`，或由已注册 Profile 支持的其它名称），必须设置 `model` 与 `url`。`provider` 默认 `openai_compatible`（旧别名 `openai` 同样可用）；`aoc_signed` 通过 `auth.app_key_env` 与 `auth.app_secret_env` 支持 AOC 签名。`description`、`timeout`、`verify_ssl`、`enable_thinking` 可选，`api_key_env` 指定保存密钥的环境变量。该文件被 Git 忽略且不含密钥（密钥字段填的都是环境变量名）；`LLM_CONFIG_FILE` 可指定其它路径。新协议通过 `common/llm/config/model_sources.py` 注册 provider profile，无需改动配置加载器。

修改配置后需要重启进程，因为模型客户端按进程缓存。模型设置仍在 `.env` 时运行 `python -m scripts.migrate_llm_config`；仍在旧 JSON 时运行 `python -m scripts.migrate_legacy_llm_json`。工具不会输出密钥，遇到冲突会中止；旧 JSON 的自定义请求模板需先实现 Profile。

## 5. FAQ

### 5.1 自定义处理器未生效
**现象描述**：注册了自定义处理器，但调用时仍使用默认处理器。

**可能原因**：
1. 注册操作在获取处理器之后执行
- 2.注册的接口类型与实际使用的不匹配
- 3.自定义处理器未正确继承BaseHandler

**解决办法**：
- 1.确保在应用启动时、任何业务处理之前完成注册
- 2.检查注册和获取时使用的InterfaceType是否一致
- 3.确认自定义处理器正确继承了BaseHandler并实现了handle方法

### 5.2 新模型配置不生效？

**现象描述**：修改 `models.yaml` 或 `.env` 后未生效。

**可能原因**：
1. `models:` 下没有该能力的条目。
- 2. 该能力缺少 `model` 或 `url`。
- 3. 进程环境变量覆盖了 `.env`。
- 4. 修改配置后未重启服务。

**解决办法**：
- 1. 检查能力名称与为其选择的 provider profile。
- 2. 重启服务；模型客户端按进程缓存。
- 3. 确认所选 profile 与目标接口协议相符。

### 5.3 模型调用报错 "Unable to extract..."

**现象描述**：调用 `embed()` 或 `rerank()` 时报 `ValueError: Unable to extract ...`

**可能原因**：所选 provider profile 与接口响应格式不匹配。

**解决办法**：
- 1. 检查实际响应结构，避免输出凭据和提示词。
- 2. 在 `common/llm/config/model_sources.py` 注册正确映射的 profile。
- 3. 为新增 profile 补充响应解析测试。


### Host Agent 运行时

顶层 `host_agent` 包提供工作流执行宿主，负责 A2A server、Workflow Engine 调用、执行事件包装和生命周期管理。运行配置、AgentCard 加载、Engine Client 创建和业务策略均由 sample composition root 注入；任务内容、条件路由、SelfLoop 和协商回复由 ControlPoint 实现提供，示例 SPN 策略位于 `samples/spn_host_agent`。使用以下命令启动：

```bash
python -m samples.start_agents_server
```

编排中心持有 UI 提交的 PSOP。执行中心下发工作流时会把 PSOP 快照放入 A2A metadata；直接按意图执行时，Host Agent 再通过配置的 Workflow Repository 查询编排中心。

### 沙箱验证

沙箱验证与正式执行相互独立。静态校验检查 DAG、`context_from`、Agent/Skill 和 Task-T/Negotiation-T 能力；Stub 执行复用真实 Workflow Engine 调度路径，但把远端任务内容生成和 A2A 调用替换为本地沙箱输入与 Stub。已保存工作流按 ID 启动；编辑器中的未保存或模板副本可以携带当前画布的 `psop` 快照启动，后端会用 `PSOP` 模型校验快照。报告记录 pass/warning/fail、执行路径、上下文链路、Stub 交互、风险和建议。

沙箱通过只表示结构和调度逻辑可运行，不表示真实 Agent 的业务输出正确。沙箱报告与正式执行记录分开存储，前端使用 `SANDBOX` 标识区分。删除运行中的验证时，会先取消后台任务，再删除报告。

沙箱报告文案来自 `orchestrate/sandbox/locales/{zh,en}.json` 资源文件；前端启动请求携带 `zh` / `en`，前端固定枚举值继续由 `workflow-designer/src/locales/*.json` 映射。新增检查项或建议时不要在业务代码中拼接用户可见句子，应同时维护两种语言的资源文件。


## 6. 安全与 TLS 配置

### 6.1 前端登录认证

内部 API（`/rest/v1/orchestrate/*`）支持令牌认证，提供两种模式：

**数据库模式（`persistence_mode=postgresql` 或 `mysql`）**：
- **用户存储**：`database/utils/user_store.py` -- 对 PostgreSQL/MySQL `users` 表进行 CRUD 操作，密码使用版本化 bcrypt 哈希
- **自动初始化**：`start.py` 启动时调用 `seed_admin_if_empty()` 创建默认 admin 用户（密码：`OpenAN@2026`）
- **注册**：提供 `POST /auth/register` 接口，校验用户名格式，前端校验密码复杂度
- **用户管理**：`GET /auth/users`（列表）、`DELETE /auth/users/{username}`（删除，admin 不可删）
- **认证模块**：`orchestrate/server/auth.py` -- `SessionStore` 将令牌映射到 (用户名, 过期时间)，`auth_middleware`
- **认证接口**：`POST /auth/login`、`POST /auth/register`、`POST /auth/logout`、`GET /auth/check`、`GET /auth/users`、`DELETE /auth/users/{username}`
- **is_auth_enabled()**：根据 `persistence_mode` 判断 -- PostgreSQL/MySQL 模式查 `has_any_user()`，file 模式检查 `access_password` 配置

**文件模式（`persistence_mode=file`）**：
- **配置**：在 `etc/conf/server.conf` 中设置 `access_password`（SHA-256 哈希值）和 `access_token_ttl`
- 单一 `admin` 用户，密码来自配置，不支持注册和用户管理
- 数据库不可用时回退到此模式

**两种模式共通**：
- **令牌传递**：会话 Cookie（`enable_https=true` 时为 `Secure`，且 `HttpOnly`、`SameSite=Lax`），非浏览器客户端可用 `Authorization: Bearer <令牌>`。不再支持查询参数传递令牌；`EventSource` 会自动携带 Cookie
- **密码哈希**：前端经 TLS 原样发送明文密码；由后端负责哈希（数据库模式下按用户加盐，文件模式下与配置的 SHA-256 值比对）
- **关闭认证**：`access_password` 为空且数据库无用户时认证关闭（向后兼容）

### 6.2 TLS/HTTPS 配置

服务端 HTTPS 通过 `etc/conf/server.conf` 配置：

| 配置项 | 说明 |
|--------|------|
| `enable_https` | 启用 HTTPS |
| `verify_client` | 要求客户端证书（mTLS 双向认证） |
| `ssl_certfile` | 服务器证书 |
| `ssl_keyfile` | 服务器私钥（加密存储） |
| `ssl_keyfile_password` | 私钥密码文件 |
| `ssl_ca_certs` | CA 信任库 |

证书校验要求（`common/cert/cert_validator.py`）：
- RSA：密钥长度 >= 3072 位
- ECDSA：密钥长度 >= 256 位

> **仅限开发、测试和 Demo：** 本工具用于快速启动，生成的 CA、服务端证书、客户端证书和私钥不得用于生产环境。生产环境必须使用受信任公共 CA 或企业内部 CA，并遵循组织的证书管理规范。

生成合规的自签名证书：
```bash
python -m generate_selfsign_cert etc/ssl serverAuth
```

新生成的 TLS 证书默认带 SAN：`DNS:localhost`、`IP:127.0.0.1`、`IP:::1`。
部署到其他地址时，用可重复的 `--dns` / `--ip` 指定实际访问地址；显式选项会替换默认 SAN 列表：

```bash
python -m generate_selfsign_cert etc/ssl-new serverAuth --dns orch.example.test --ip 192.0.2.10
```

SAN 必须与客户端 URL 的主机匹配，IP 必须使用 `--ip`，仅设置 CN 或信任证书不能解决 SAN 缺失。
旧证书不会自动更新；工具拒绝覆盖已有证书或私钥。已有部署请在新目录生成，备份并部署匹配的
证书/私钥后重启服务；需要重新分发信任证书的客户端应同步更新。不要覆盖用于校验客户端身份的 CA 信任库。
`dataSigning` 不添加 TLS SAN，也不接受命令行 SAN 选项。

**启用 HTTPS 步骤：**

1. 生成证书（见上方命令）。`serverAuth` 会直接产出 `server.conf` 期望的部署文件
   （`server.cer`、`trust.cer`、`server_key.pem`、`cert_pwd`）；加 `--plain-key` 会额外
   生成 Nginx 使用的未加密私钥 `server_key_nopass.pem`。无需手工复制或创建密码文件。
   默认口令路径为 `etc/ssl/cert_pwd`。所有已有输出均拒绝覆盖，包括口令和客户端文件；
   新目录换证后须重签客户端证书并分发新信任材料。明文口令文件与私钥一起保护，
   Windows 使用服务账号 ACL。单独生成签名测试材料可用
   `python -m generate_selfsign_cert etc/sign_cert dataSigning`，输出
   `sign.cer`、`sign_key.pem` 和 `cert_pwd`，不自动启用业务签名。

2. 修改 `etc/conf/server.conf`：`enable_https=true`，如需 mTLS 设 `verify_client=true`。

3. 在 `etc/conf/server.conf` 中设置 `client_verify_server=false`（跳过对其他服务的证书校验）。

4. 重启后端服务。

**签发客户端证书（`verify_client=true` 时）：**

自签名服务器证书同时作为自身的 CA（`trust.cer` 为其副本，已内置 `CA:TRUE` 与
`keyCertSign`）。为需要接入的客户端签发证书：

```bash
python -m generate_selfsign_cert etc/ssl serverAuth --issue-client dev-proxy
```

- 输出 `etc/ssl/dev-proxy-client.cer` 与 `dev-proxy-client.key`（未加密，Linux 上 600 权限）；
  密码自动从 `cert_pwd` 读取，无需交互。
- `dev-proxy` 是 Vite 开发代理的约定名称：`workflow-designer/vite.config.js` 启动时自动读取
  这对文件向本服务出示客户端证书，签发后需重启 `npm run dev`。
- 本地或 Demo Nginx 代理场景：浏览器无法出示客户端证书，由 Nginx 代为出示——用
  `proxy_ssl_certificate` / `proxy_ssl_certificate_key` 配置这对文件，
  `proxy_ssl_trusted_certificate` 指向 `trust.cer`（模板见
  `workflow-designer/nginx.conf.template` 的注释块）。

证书链要求：客户端证书必须由 `ssl_ca_certs` 信任库中的 CA 签发。本工具生成的服务器证书
已满足该要求；使用外部 CA 时，请用该 CA 签发客户端证书。

### 6.3 客户端 SSL 上下文

出站 HTTPS 调用（如编排中心 -> 注册中心）使用共享的 SSL 上下文工厂：

- **模块**：`workflow_engine.client.ssl_context` -- `create_ssl_context()`（由 workflow-engine SDK 提供）
- **配置**：`server.conf` 中的 `client_verify_server`（默认 `false`，向后兼容）
- **功能**：CA 信任库校验、可选 mTLS 客户端证书、CRL 吊销检查、密码套件
- **使用方**：`orchestrate/registry_client/client.py` 中以 `create_ssl_context(verify_server=...)` 调用，并传给 `httpx.AsyncClient(verify=...)`

`client_verify_server=false` 时返回 `False`（跳过校验），允许连接自签名证书的服务器。生产环境应设为 `true` 并配置正确的 CA 信任库。

### 6.4 外部 API 保护

外部 API（`/api/v1/*`）通过 mTLS 在 TLS 层保护。无需应用层认证中间件——TLS 握手阶段即拒绝无有效客户端证书的连接，请求不会到达应用层。
